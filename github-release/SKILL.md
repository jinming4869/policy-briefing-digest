# 政策速递与通报整理 Skill v2

本 skill 用于把政策、监管通报、行业规则、法院案例、平台规则、海外合规动态或官方公众号信息，处理成可进入公司周报的内容。核心目标不是“摘要新闻”，而是为游戏/互联网公司提供可核验、可追溯、可执行的政策判断。

v2 的重点是两条：

1. **流程丝滑化**：自动识别任务类型，优先调用正确工具链，避免临时找 skill、临时找 CLI、临时处理编码、路径、认证和写入方式。
2. **内容可迭代**：把用户修改后的优质版本纳入范例库和写作规则，后续生成时自动参考相似案例，提高栏目判断、业务相关性和文风质量。

每次完整执行至少产出：

1. 官方来源清单。
2. 政策链条和上下文判断。
3. 可直接进入周报的“政策描述 + 政策解读”。
4. 业务影响和待确认事项。
5. 如涉及飞书写入：写入位置、回读校验和运行报告。
6. 如涉及用户修订稿：差异分析、可迁移规则、范例库更新建议。

## 0. 任务路由：先判断任务类型

开始任何处理前，必须先判断任务类型。不得在未分类的情况下直接抓网页、写稿或打开浏览器。

### 0.1 任务类型

#### A. `policy_digest_draft`

用户提供政策来源、截图、公众号正文或新闻线索，要求转化为政策速递条目。

执行：

1. 读取本 skill。
2. 获取并核验来源。
3. 判断栏目。
4. 生成周报条目。
5. 输出待核验项。

#### B. `policy_digest_writeback`

用户同时提供来源信息和飞书/wiki/doc/docx 目标地址，要求写入文档。

执行：

1. 读取本 skill。
2. 读取飞书/文档写入规则。
3. 先做 CLI/API 预检。
4. 获取并核验来源。
5. 生成条目。
6. 写入飞书。
7. 回读校验。
8. 输出运行报告。

#### C. `policy_digest_revision`

用户提供自己修改后的更好版本，要求分析、吸收或用于优化后续生成。

执行：

1. 对比原稿和用户修订稿。
2. 分析用户稿好在哪里。
3. 抽取可迁移规则。
4. 建议更新 gold cases、anti-patterns、rubric 和 style rules。
5. 用新规则回归测试同类写作。

#### D. `policy_digest_review`

用户要求检查一整期周报、排版、栏目、事实、文风或质量。

执行：

1. 按栏目检查结构。
2. 检查事实链条和来源层级。
3. 检查业务相关性。
4. 检查文风和禁用句式。
5. 给出逐条修改建议。

### 0.2 强触发词

出现以下任一关键词，必须优先使用本 skill：

- 政策速递、政策周报、通报整理、行业监管动态、政策法规发布、产业政策指引、海外合规风向。
- 政策解读、业务启示、对游戏公司而言、互联网公司合规、公司周报。
- 写入飞书、飞书 wiki、飞书文档、docx token、lark-cli、feishu-cli。
- 微信公众号政策信息、mp.weixin.qq.com、官方公众号。
- 网信、工信、通管、公安、市监、版号、数据出境、个人信息保护、未成年人保护、平台规则、出海合规。

## 1. 运行环境与工具链

### 1.1 运行平台

本 skill 在 Windows（PowerShell 5.1+）上开发和验证。macOS / Linux 用户可参考工具脚本逻辑自行改写（核心脚本均为 PowerShell，约 60 行以内）。

### 1.2 依赖工具

| 工具 | 用途 | 安装方式 |
|------|------|----------|
| Python 3.10+ | 数据处理 | `winget install python` 或 [python.org](https://python.org) |
| Node.js 18+ / npm | 辅助脚本 | `winget install nodejs` 或 [nodejs.org](https://nodejs.org) |
| 飞书 CLI (`lark-cli`) | 文档读写 | `npm i -g lark-cli`（见 [§飞书接入](#飞书接入)） |
| PowerShell 5.1+ | 工具脚本运行环境 | Windows 预装 |

项目工具脚本（`tools/` 目录下）：

- `tools/feishu_write.ps1` — 飞书文档一键写入（自动 fetch→replace→verify）
- `tools/doc_convert.ps1` — .doc 转 .docx/.txt（调用 Word COM，需本机安装 Microsoft Word）
- `tools/gov_search.ps1` — gov.cn 政策文件库精确搜索

调用方式：`powershell -NoProfile -File tools/<script>.ps1 [参数]`

### 1.3 执行约束

- Agent 应使用预设的工具路径或环境变量，不使用裸命令临时探路。
- PowerShell 可能优先解析到不可用的 `.ps1`，始终用 `.cmd` 后缀调用 npm 全局命令。
- 飞书文档写入使用 `lark-cli.cmd`，不要调用 `lark-cli.ps1`。
- 向飞书写入中文 XML/Markdown 时，优先使用 UTF-8 文件和 `--content @relative-file`。
- 避免用 PowerShell 管道传中文正文，以免编码降级为问号。

### 1.4 环境预检

涉及飞书写入时，先执行预检，不要先打开 Chrome。

建议检查项：

1. `lark-cli.cmd` 是否存在。
2. `lark-cli doctor` 是否通过。
3. 是否可读取目标 wiki/docx/doc。
4. 是否可解析 URL 到 wiki token 或 docx token。
5. 是否可定位目标栏目标题。
6. 是否可回读受影响区域。

如果 CLI/API 不可用，再考虑浏览器 UI。浏览器 UI 只能作为兜底。

## 2. 工具优先级

### 2.1 飞书写入优先级

涉及飞书或在线文档写入时，必须按以下顺序：

1. 飞书/Lark CLI。
2. 飞书/Lark API 或 MCP 连接器。
3. 本地脚本封装的飞书 API。
4. 浏览器自动化。
5. 交付可粘贴文本并说明无法可靠写入。

不得把浏览器 UI 自动化作为主写入方式。若不能可靠回读，停止并交付可粘贴文本。

### 2.2 微信公众号读取优先级

微信公众号常有访问限制。按以下顺序处理：

1. 直接读取 URL 标题、发布时间和正文。
2. 使用浏览器读取。
3. 搜索官方转载、政府官网或上位政策原文。
4. 要求用户粘贴正文或截图。
5. 仅在没有文本时使用截图识别。

不得在无法读取正文时凭标题改写。不得把公众号名称自动当作发布机构。

### 2.3 来源核验优先级

按以下顺序使用来源：

1. 官方文件原文。
2. 官方答记者问、政策解读、新闻发布会实录。
3. 主管部门转载的权威媒体报道。
4. 地方政府或部门官网。
5. 企业公告、平台规则页面。
6. 权威新闻社。
7. 媒体报道、律所文章和公众号文章。

媒体报道只能提供线索。政策描述中的核心事实，原则上必须回到官方原文。

## 3. 固定频率与事件触发

### 3.1 固定频率

- 每周收集一次。
- 每周五提交。
- 版号信息重点关注每月 22 日左右。
- 周报定稿前，必须回查本周已收集条目的官方链接和标题链接。
- 节假日前后需额外检查国务院、部委、地方政府是否集中发布政策。

### 3.2 事件触发

出现以下任一情况时，执行本 skill：

- 用户提供政府官网、官方公众号、媒体报道、截图或复制文本。
- 出现与游戏、互联网平台、数据合规、未成年人保护、广告、算法、支付、招投标、财政补贴相关的政策。

## 4. 信息栏目与重点来源

政策速递分为四个固定栏目。收集时先判断栏目，再决定分析口径。

### 4.1 行业监管动态

关注内容：

- 游戏版号发布。
- APP、SDK、小程序通报。
- 专项行动。
- 培训会。
- 备案登记。
- 法院经典判例。
- 网络安全、个人信息保护和未成年人保护相关执法。

推荐关注：

- 工信部：工信微报。
- 通管局：北京通信业、上海通信圈。
- 网信办：网信中国、网信北京、网信上海。
- 市监局：市说新语、北京市场监管、上海市场监管。
- 公安部：公安部、公安部网安局、国家网络安全通报中心。
- 版号：国家新闻出版署。
- 法院经典判例：最高人民法院、北京互联网法院、网络诉讼圈。
- 信通院：CAICT互联网法律研究中心。

执行要求：

- APP 通报必须记录发布机构、检测时间、通报对象数量和整改期限。
- 版号发布须记录审批信息发布时间、游戏名称、申报类别和出版单位。
- 法院案例须区分典型案例、指导性案例、普通裁判文书和媒体报道。
- 培训会只在出现明确监管口径、检查方向或业务要求时进入周报。

### 4.2 政策法规发布

关注内容：

- 游戏、网络安全、个人信息保护相关法律。
- 行政法规、部门规章、规范性文件。
- 国家标准、行业标准、团体标准。
- 征求意见稿和正式稿。
- 政策解读和答记者问。
- 已发布制度的首单落地、配套细则或实施案例。

推荐关注：

- CAICT 互联网法律研究中心。
- 中国政府网。
- 中国网络空间安全协会。
- 国家标准全文公开系统。

执行要求：

- 标准类文件必须区分“发布”“征求意见”“实施”。
- 征求意见稿必须记录意见反馈截止日。
- 正式稿必须和征求意见稿比较主要变化。
- 法律法规不得只引用媒体报道，必须回到官方文本。
- 制度落地案例必须说明上位制度、落地时间、适用主体和可复制的业务流程。

### 4.3 产业政策指引

关注内容：

- 游戏、数字文创、数字经济相关产业扶持。
- 民营企业营商环境政策。
- 地方园区入驻政策。
- 科技创新、出海、文化贸易相关支持。
- 京沪之外，必要时扩大到浙江、广东等游戏大省。

推荐关注：

- 各地经信委、商务厅、文旅部门和发改部门网站。
- 中国政府网。
- 重点省市政府官网。
- 重点园区管委会官网。

执行要求：

- 必须确认政策是否公开发布。
- 必须确认申报条件和兑现条件。
- 涉及补贴、税收返还、零租金、开票奖励时，必须提示合规复核。
- 园区招商公众号只能作为线索，不得单独作为政策依据。

## 7. 建立分析 context 的执行规范

### 7.1 纵向比较

任何政策分析都要先问：

- 这件事最早从哪个中央文件、会议或专项行动开始。
- 中间有哪些执行文件、地方细则或通报案例。
- 本次是新规则、阶段性汇报、正式落地，还是后续处置。
- 后续是否存在实施日期、整改期限或配套文件。

写法要求：

- 使用“时间 + 文件 + 变化”结构。
- 不要只罗列文件名。
- 每个文件必须说明它在链条中的作用。

示例：

`2022年中央文件提出治理地方保护，2025年《建设指引》细化地方执行规则，本次报告则把前期部署纳入阶段性汇报，并列出后续检查方向。`

### 7.2 横向比较

根据事项类型选择比较对象：

- 同一机构近期是否连续发布类似通报。
- 其他部门是否同步治理同一问题。
- 北京、上海、浙江、广东是否已有相近产业政策。
- 征求意见稿与正式稿是否存在实质变化。
- 国内监管口径与海外监管口径是否出现同向趋势。
- 游戏行业是否比其他互联网场景更敏感。

写法要求：

- 比较必须服务于业务判断。
- 没有足够证据时，不写“趋势”。
- 不为了横向比较而堆地区、堆部门。

### 7.3 上下级关系

必须区分：

- 中央文件：定方向。
- 部委文件：定规则。
- 地方文件：定执行。
- 园区政策：定申报和兑现。
- 企业案例：显示风险场景。
- 首单落地：显示制度如何被实际适用，但不等同于新规则发布。

涉及地方政策时，要判断其是否可能受上位规则复核。例如地方招商、财政补贴和返税政策，应回查公平竞争审查、财政纪律和全国统一大市场相关文件。

### 7.4 征求意见稿与正式稿

如果存在两个版本，必须比较：

- 适用对象是否变化。
- 企业义务是否新增。
- 处罚责任是否变化。
- 过渡期是否变化。
- 对游戏业务影响是否更明确。

不得只写“正式稿落地”。必须说明正式稿相对征求意见稿改了什么。

### 7.5 关键点判断

每条政策只抓一个最重要的点。判断标准：

- 是否直接改变公司业务动作。
- 是否影响产品上线、运营或投放。
- 是否带来合规整改义务。
- 是否提供可申报的政策利好。
- 是否提示地方或海外监管风险。

不要把所有信息平均展开。政策速递服务对象是公司业务，不是政策课堂。

### 7.6 上位法与下位清单的交叉比对

当一条政策涉及下位清单对上位法规则做量级调整时，必须比对两份文件中的具体门槛数字，精确写出差异（从X万提到Y万），并解释具体企业为何受益。参见 gold case `20260626_sh_data_negative_list`。

## 8. 业务相关性判断

对游戏公司，优先关注能改变以下事项的政策：

- 游戏版号和上线节奏。
- 内容审核和备案登记。
- 未成年人保护、实名制、充值和退款。
- 个人信息保护和数据出境。
- 算法推荐和广告投放。
- 买量素材、直播营销和用户权益。
- 应用商店、渠道联运和小游戏平台。
- 地方文创扶持、园区入驻和研发中心设立。
- 政府采购、招投标和财政补贴。
- 出海合规和海外平台规则。

无法落到业务动作的政策，降级为背景跟踪。

### 8.1 数据出境专项判断

涉及数据出境、个人信息跨境、集团内数据共享或海外运营时，必须检查以下场景：

- 海外发行。
- 全球账号体系。
- 跨境客服工单。
- 支付、订单和退款处理。
- 广告归因和投放效果分析。
- 设备标识、日志数据和风控数据。
- 海外云服务和 CDN。
- 集团内统一会员、CRM、BI 或数据湖。
- SDK、第三方分析工具和海外供应商。

写解读时，不得只写“企业应关注数据出境合规”。必须说明哪些数据、哪些业务链路、哪些流程可能触发备案或评估。

### 8.2 APP/SDK 通报专项判断

涉及 APP、SDK、小程序通报时，必须检查：

- 是否未经同意收集个人信息。
- 是否超范围收集。
- 是否未明示第三方 SDK。
- 是否权限申请目的不清。
- 是否缺少账号注销、更正删除、投诉渠道。
- 是否涉及未成年人信息。
- 是否涉及广告弹窗、个性化推荐关闭或自动续费。

解读应落到产品、SDK 接入、权限弹窗、隐私政策和渠道上架检查。

### 8.3 地方产业政策专项判断

涉及园区、补贴、入驻、招商、奖励时，必须检查：

- 政策是否公开发布。
- 申报主体是否有真实业务落地。
- 补贴是否与税收、开票额或地方留成挂钩。
- 是否可能触及公平竞争审查、财政纪律或全国统一大市场要求。
- 是否需要业务、财务、法务、GR 共同复核。

## 9. 政策描述写作规范

政策描述只写事实，不写判断。

必须包括：

- 日期。
- 发布机构。
- 文件或通报名称。
- 主要对象。
- 核心措施。
- 期限或后续安排。
- 与上位政策或上一批次的事实关系。

推荐结构：

`YYYY年M月D日，发布机构发布/转载/提请审议《文件名》。文件/报告/通报指出……，要求……，并提出……。如存在整改期限、检查数量或处置结果，应在本段写明。`

不得在事实段写：

- “释放监管信号”。
- “监管持续加码”。
- “行业进入新阶段”。
- “值得企业高度重视”。
- “对企业提出更高要求”。

---

## 10. 政策解读写作规范

解读必须回答四个问题：

1. 这件事从哪里来。
2. 本次变化在哪里。
3. 为什么与游戏/互联网公司有关。
4. 公司可能在哪个具体场景中遇到问题。

推荐结构：

`本次事项溯源于……（附超链接）。此前……，本次……。对游戏公司而言，……。`

推荐内容：

- 纵向回溯关键节点。
- 横向比较相近地区、部门或行业。
- 找到本条新闻最重要的点展开。
- 给出具体风险提示或政策利好建议。

禁止写成：

`企业应密切关注政策变化，完善合规体系。`

应改为：

`如果公司准备新设地方主体申请文创补贴，应先确认该主体是否有真实团队和业务合同。只迁注册地、不落业务，后续可能遇到补贴复核。`

### 10.1 动态决策协议

在生成解读之前，agent 必须主动识别不确定性，并生成决策卡片（Decision Card JSON）向用户确认。

**触发条件**（满足任意一条即生成决策卡片，不得自行假设答案）：

1. **信息缺口**：政策原文无法从公开来源获取，或搜索未返回完整文本。需明确说明缺失的具体内容，并给出"上传文件 / 用公开信息继续 / 帮我搜索"三个选项。
2. **业务优先级模糊**：政策可能影响多个业务线（数据合规、出海、广告、未成年人等），但无法判断当前哪一条对公司最紧急。需列出 2—5 个实际相关的维度，给出理由。
3. **分析方向冲突**：政策存在多个可深入的方向（纵向链条追溯、横向比较、门槛对比、风险推演等），但篇幅限制只能深挖一个。需根据本条政策的具体内容动态生成选项，而不是每次从固定模板中选。

**输出格式**：在对话中输出如下 JSON 代码块，告知用户粘贴到 `workbench.html`：

```json
{"decisions":[
  {"id":"唯一id","title":"卡片标题","detail":"具体描述","type":"single|multi","options":[{"id":"选项id","label":"选项文字"}]}
]}
```

**禁止**：跳过决策协议，在信息不足或方向模糊时自行推断答案并直接输出完整解读。

### 10.2 双版本输出模式

每条政策的解读部分，先产出两个版本，再按用户指示精修。

**长版（参考版）**：
- 字数：500—1000 字。
- 用途：辅助用户厘清问题、掌握背景知识，不直接进入周报。
- 内容：可包含详细政策链条、横向比较、法条原文引用、行业影响面分析、补充案例等。
- 文风：允许适度展开，无需严格遵守禁用句式列表，但保持专业口吻。

**短版（正式版）**：
- 字数：220—360 字，严格按本 skill 第 10 节和第 11 节要求。
- 用途：可直接进入周报。
- 内容：只抓一个最重要的判断点，删掉旁支补充、实操指南、例外条款和尾注式"需注意"。
- 文风：直接、简洁、准确，禁用句式全面生效。

**输出格式**：
```
### 📖 长版参考
<500-1000字解读>

### 📄 短版
<220-360字解读，可直接用于周报>
```

**执行原则**：
- 短版不是长版的摘要，而是对长版做减法——删到只剩一条推力。
- 如果用户对短版做了进一步压缩（自己上手改），视为高价值信号，必须做差异分析并提取可迁移规则（见第 14 节）。

## 11. 文风限制

### 11.1 禁用句式

不要使用：

- `不是……而是……`
- `最稳`
- `一方面……另一方面……`
- `总体来看`
- `值得注意的是`
- `释放信号`
- `监管趋严`
- `持续加码`
- `形成闭环`
- `赋能`
- `底层逻辑`
- `高质量发展`作泛泛结论

### 11.2 罗列限制

单句中不要出现超过 3 个以顿号隔开的词组。

不写：

`数据、算法、广告、支付、未成年人、消费者权益等领域均需关注。`

改写：

`游戏公司应优先检查数据和广告合规。若产品面向未成年人，还要单独核查实名制和充值限制。`

### 11.3 抽象词限制

少用：

- 强化。
- 推进。
- 完善。
- 加强。
- 促进。
- 压实。
- 深化。
- 常态化。
- 机制化。

可以使用政策原文中的抽象词，但必须接具体事实。

### 11.4 篇幅限制

- 政策描述控制在 180—260 字。
- 政策解读控制在 220—360 字。
- 单段不超过 6 句。
- 每句尽量不超过 45 字。

---

## 12. 输出格式

### 12.1 标准条目

格式：

`X. **[标题](官方链接)**`

`政策描述段`

`解读：政策解读段`

### 12.2 标题规则

标题必须加粗并放链接。

标题包括：

- 发布机构或报告主体。
- 行为。
- 核心对象。

示例：

`**[国务院报告提出整治地方招商引资乱象和违规财政补贴问题](官方链接)**`

不要写：

`全国统一大市场建设迎来重大变化`

### 12.3 链接规则

- 标题链接必须指向官方原文。
- 如果只有主管部门转载稿，标题链接可以指向转载稿，但描述中要说明“转载”。
- 海外新闻尽量链接外国监管机构官网或权威新闻社。
- 定稿前必须逐条打开链接检查。

## 13. 飞书或在线文档写入协议

用户明确要求写入飞书时，优先使用 `tools/feishu_write.ps1` 一键写入：

```powershell
powershell -NoProfile -File tools/feishu_write.ps1 -Doc "wiki-token" -HeadingId "h4-block-id" -DescFile "desc.xml" -InterpFile "interp.xml"
```

手动流程（脚本不可用时）：

1. 先查找已配置的飞书 API、CLI 或连接器。
2. 运行 CLI/API 预检。
3. 解析目标 URL，确认 wiki/doc/docs/docx 类型。
4. 如为 wiki，解析 wiki token 到 docx token。
5. 读取文档结构。
6. 定位目标栏目 heading。
7. 确认插入位置。
8. 写入本期条目。
9. 回读受影响区域。
10. 检查标题链接是否正确。
11. 如果是在上一期基础上创建副本，还要更新标题期数、速递日期、往期回顾和权限。

### 13.1 文档维护规范

每次在上一期基础上创建副本时，必须修改：

- 标题期数。
- 速递日期。
- 本期新增条目。
- 往期回顾。
- 链接。

权限设置：

- 文档权限设为“仅协作者可访问”。

往期回顾：

- 只引用最近四期。
- 不保留过早期数。
- 检查每条回顾链接是否仍可打开。

### 13.2 写入失败处理

如果不能可靠写入或回读：

1. 停止浏览器 UI 反复尝试。
2. 交付可直接粘贴的周报条目。
3. 说明失败位置。
4. 输出下一步需要用户确认的信息。
5. 不声称已经写入。

## 14. 内容迭代协议：吸收用户修改稿

当用户提供“我修改过后的更好版本”时，必须执行本协议。目标不是称赞用户版本，而是提炼可迁移规则，并更新后续生成标准。

### 14.1 差异分析维度

逐项比较原稿与用户稿：

1. **事实界定**：是否更准确地区分新规、落地案例、通报、处罚、征求意见、政策解读。
2. **栏目归属**：是否更符合行业监管动态、政策法规发布、产业政策指引、海外合规风向。
3. **政策链条**：是否补上上位文件、前序政策、地方细则、执行案例。
4. **业务相关性**：是否落到游戏/互联网公司的具体业务链路。
5. **判断力度**：是否避免夸大，是否把推断和事实分开。
6. **篇幅控制**：是否删去无效背景、新闻腔和官方套话。
7. **文风**：是否更接近内部政策速递，而不是新闻稿、法律备忘录或 AI 总结。
8. **可执行性**：是否能帮助内部读者判断是否需要自查、跟进、申报、复核或调整流程。

### 14.2 可迁移规则提取

每次差异分析后，必须抽取 5—10 条可迁移规则，格式为：

`当出现【事项类型】时，应当【写法/判断规则】，避免【常见错误】。`

示例：

`当事项是制度首单落地时，应写成“政策落地进展”，避免误写成“新规发布”。`

### 14.3 范例库更新建议

如果用户稿明显优于原稿，建议写入：

- `examples/gold_cases/<topic>_<date>.md`
- `examples/comparison_notes/<topic>_<date>_delta.md`
- `content/anti_patterns.md`
- `content/writing_rubric.md`
- `content/style_rules.md`

如果当前环境可以写文件，直接创建或更新这些文件。否则输出可复制的更新片段。

## 15. 内容质量评分标准

每条进入周报的内容必须通过以下检查。

### 15.1 事实准确性

- 发布机构准确。
- 日期准确。
- 官方标题准确。
- 文件类型准确。
- 官方链接可打开。
- 不把媒体线索写成官方结论。
- 不把地方案例拔高成全国规则。
- 不把政策落地案例误写成新政策发布。

### 15.2 栏目匹配

- 行业监管动态：执法、通报、专项行动、备案登记、版号、经典案例。
- 政策法规发布：法律、法规、规章、标准、规范性文件、征求意见、正式稿、配套实施、制度落地。
- 产业政策指引：产业扶持、园区、补贴、招商、营商环境、科技创新、出海支持。
- 海外合规风向：境外监管、海外平台规则、域外执法、国际合规趋势。

### 15.3 游戏/互联网业务相关性

必须至少落到一个具体场景：

- 游戏版号和上线节奏。
- 内容审核和备案登记。
- 未成年人保护、实名制、充值和退款。
- 个人信息保护和数据出境。
- 算法推荐和广告投放。
- 买量素材、直播营销和用户权益。
- 应用商店、渠道联运和小游戏平台。
- 地方文创扶持、园区入驻和研发中心设立。
- 政府采购、招投标和财政补贴。
- 出海合规和海外平台规则。
- 客服、支付、SDK、云服务、集团内共享、数据分析。

### 15.4 写作质量

- 事实段不写判断。
- 解读段不复述事实。
- 每条只抓一个最重要的点。
- 不写泛泛“企业应关注”。
- 不写新闻稿式结尾。
- 不用禁用句式。
- 不堆术语。
- 不用过多顿号并列。
- 推断必须标明依据。

## 16. 质检清单

交付前逐项检查：

- 标题是否加粗。
- 标题是否放官方链接。
- 链接是否能打开。
- 发布机构是否准确。
- 日期是否准确。
- 是否区分转载来源和原始发文机关。
- 是否区分征求意见稿和正式稿。
- 是否区分报告、通知、通报、处罚、标准和制度落地案例。
- 是否有纵向政策链条。
- 是否有必要的横向比较。
- 是否写出本条最重要的点。
- 是否有游戏/互联网业务场景。
- 是否出现超过 3 个顿号词组。
- 是否出现禁用句式。
- 是否把推断写成事实。
- 是否把媒体线索写成官方结论。
- 是否存在无出处企业名称。
- 如涉及飞书，是否回读校验。
- 如涉及整期周报，是否更新标题期数、速递日期和往期回顾。
- 如涉及权限设置，是否确认权限为“仅协作者可访问”。

任何核心事实无法核验时，不输出定稿。交付“可用草稿 + 待核验项”。

### 17.3 上下文窗口口径

上下文窗口不得猜测。只报告可观察事实：

- 是否仍在同一会话上下文。
- 是否发生上下文压缩、重启或切换。
- 环境是否提供 token usage。
- 如果无法精确统计，必须明确写“当前环境未提供精确 token / context window 数据”。

示例：

`上下文窗口：观察到 1 个会话上下文，未见压缩或切换；当前环境未提供精确 token 占用。`

## 18. 交付物规则

### 18.1 完整执行

每次完整执行后交付：

1. 官方来源清单。
2. 政策链条简表。
3. 可直接粘贴的周报条目。
4. 业务影响判断。
5. 待确认事项。
6. 如涉及飞书：写入与回读结果。
7. 运行报告。

### 18.2 只要求压缩或改写

如果用户只要求压缩或改写，只交付改写文本，不解释流程。

### 18.3 写入失败或来源不足

如果来源不足或写入失败：

1. 不输出定稿。
2. 不声称完成写入。
3. 输出可用草稿。
4. 列出待核验项。
5. 说明下一步需要的最少信息。

## 19. 配套文件结构

经实际使用验证，以下结构有效：

```text
policy-briefing-digest/
  SKILL.md                     # 主文件：全流程规则
  workbench.html               # 交互式决策面板
  tools/
    feishu_write.ps1            # 飞书一键写入
    doc_convert.ps1             # .doc → .docx 转换
    gov_search.ps1              # gov.cn 政策搜索
  configs/
    feishu_targets.yaml         # 飞书文档URL + 栏目heading
  content/
    writing_rubric.md
    style_rules.md
    anti_patterns.md
    overseas_compliance_style.md # overseas compliance drafting rules
  workflow/
    feishu_writeback.md
  examples/
    gold_cases/
```

**原则**：配套文件存在的唯一理由是"独立于 SKILL.md 的价值"。如果一个文件的内容已被 SKILL.md 覆盖，不要单独存在。gold cases 只存最终定稿，不存草稿或对比稿。
